# Заявки СЭП ERP: инструкция для DevOps

## Что готово и что ещё требуется

`ERP/` содержит готовую статическую сборку. Все три формы (середина страницы,
низ страницы, модалка) отправляют `POST /api/leads` на тот же домен.
`backend/erp/` содержит отдельный запускаемый Node.js backend, тесты и lockfile.
Отправитель, SMTP envelope и получатель жёстко зафиксированы: `info@pksep.ru`.
Email посетителя используется только в `Reply-To`. Имя отправителя: «СЭП ERP».

**Выгрузка в Git не запускает backend на pksep.ru.** Нужны серверный SMTP-пароль,
ENV, Node.js, процесс backend и reverse proxy. Проверки выполнены локально с
тестовым SMTP; фактическая доставка в `info@pksep.ru` пока не подтверждена.

## Размещение и запуск

Требуется Linux, Node.js **24.13+** (Node 24 LTS), npm и доступ к SMTP по TCP 465.
SQLite встроен в Node, отдельный сервер БД не нужен. Node 24 может выводить
предупреждение о экспериментальном статусе SQLite API.

1. Публично разместить **только содержимое `ERP/`** в document root сайта
   (или в его подпапке `/ERP/`). `backend/`, `deploy/`, рабочие ENV и SQLite
   не должны быть доступны через HTTP. Клиент всегда обращается к `/api/leads`,
   независимо от подпапки размещения лендинга.
2. Скопировать `backend/erp/` в `/opt/sep-erp/backend/erp`, без `node_modules/`
   и локальных данных. Установить зависимости:

   ```sh
   cd /opt/sep-erp/backend/erp
   npm ci --omit=dev --ignore-scripts
   npm test
   ```

   Тесты используют только loopback и локальный тестовый SMTP, не реальную почту.
3. Создать непривилегированного системного пользователя `sep-erp`. Код и
   `node_modules` должны быть ему доступны для чтения, но не для записи.
4. Скопировать `.env.example` в `/etc/sep-erp/mail.env` вне document root.
   Права файла `600`, владелец `root`; systemd читает его до смены пользователя.
   Внести SMTP-пароль непосредственно на сервере. Сгенерировать отдельный
   случайный `LEADS_HMAC_SECRET` длиной не менее 32 символов, например через
   `openssl rand -hex 32`, и сохранить только в серверном ENV.
   Не передавать секреты в аргументах команд, переписке, Git или логах.
5. Проверить путь к Node 24 командой `command -v node` и `node --version`.
   В `sep-erp.service` при необходимости исправить `/usr/bin/node` на фактический
   абсолютный путь. Установить unit в `/etc/systemd/system/sep-erp.service`:

   ```sh
   sudo systemctl daemon-reload
   sudo systemctl enable --now sep-erp
   sudo systemctl status sep-erp
   curl --fail http://127.0.0.1:3001/healthz
   curl --fail http://127.0.0.1:3001/readyz
   ```

   При отсутствующем пароле/секрете backend не запустится. `healthz` проверяет
   процесс, `readyz` проверяет подключение и авторизацию SMTP (кеш 30 секунд),
   но не подтверждает доставку в почтовый ящик. Эти маршруты не нужно публиковать.
6. Вставить `nginx.conf.example` в существующий **HTTPS server block** pksep.ru.
   Не заменять целиком действующий конфиг сайта или конфигурацию лендинга чата.
   Проверить `sudo nginx -t`, затем `sudo systemctl reload nginx`.
   `X-Real-IP` должен перезаписываться nginx, а не браться из заголовка клиента.
   Backend слушает только `127.0.0.1:3001`; не открывать этот порт в интернете.
7. Проверить реальные заявки из **всех трёх форм** после выкладки фронта и API.
   Подтвердить поступление тестовых писем в `info@pksep.ru` вручную. Не проводить
   такую проверку с персональными данными реальных посетителей без согласия.

Запуск без systemd для локальной проверки (отдельный серверный ENV с путями,
доступными текущему пользователю):

```sh
cd backend/erp
npm ci --ignore-scripts
node --env-file=/absolute/private/path/mail.env server.mjs
```

В локальном ENV: `ALLOWED_ORIGINS=http://127.0.0.1:5173`, `TRUST_PROXY=false`,
`LEADS_DB_PATH=/absolute/private/path/leads.sqlite`. Vite проксирует `/api`
на порт 3001. В отдельном терминале из исходного SEP выполнить `npm run dev`.
SMTP-пароль никогда не использовать в `VITE_*` и не размещать в `ERP/`.

## ENV

Полный безопасный шаблон: [.env.example](.env.example).

| Переменная | Значение / назначение |
| --- | --- |
| `HOST`, `PORT` | `127.0.0.1`, `3001` |
| `ALLOWED_ORIGINS` | Точные origin через запятую; production `https://pksep.ru`, без завершающего `/`. При работе через www добавить его точный HTTPS origin |
| `TRUST_PROXY` | `true` только для закрытого backend за loopback nginx, иначе `false` |
| `SMTP_HOST` | `smtp.majordomo.ru`, подтвердить у почтового администратора |
| `SMTP_PORT`, `SMTP_SECURE` | `465`, `true` (TLS сразу). Для `587` задать `false`: STARTTLS обязателен, без TLS отправки не будет |
| `SMTP_USER` | `info@pksep.ru` |
| `SMTP_PASSWORD` | Пароль/пароль приложения, обязательный, только на сервере |
| `MAIL_FROM`, `MAIL_TO` | Только `info@pksep.ru`; код отклоняет другие значения |
| `LEADS_HMAC_SECRET` | Случайный секрет, минимум 32 символа; используется для необратимых keyed hash, не для SMTP |
| `LEADS_DB_PATH` | `/var/lib/sep-erp/leads.sqlite`, постоянный диск вне сайта |
| `LEADS_RATE_LIMIT` | `5` попыток с IP за 10 минут, включая невалидные запросы |
| `LEADS_GLOBAL_RATE_LIMIT` | `100` попыток всего за 10 минут |
| `LEADS_MIN_FORM_MS` | `2000`, минимальный возраст формы в мс |
| `LEADS_MAX_CONCURRENT` | `3`, одновременно выполняемых SMTP-отправки |

Логические значения принимаются строго как `true`/`false`. Проверка TLS-сертификата
всегда включена. Перед отправкой проверить SPF/DKIM/DMARC домена и настройки
ящика у провайдера. Не включать SMTP debug/логирование содержимого писем.

## Контракт API

```http
POST /api/leads
Origin: https://pksep.ru
Content-Type: application/json
Idempotency-Key: <UUID v4>
```

```json
{
  "name": "Тест",
  "contact": "visitor@example.com",
  "consent": true,
  "source": "demo-middle",
  "company": "",
  "elapsedMs": 4000
}
```

Имя 1..100 символов, контакт до 150 символов (валидный email или телефон
10..15 цифр), `consent` строго `true`, без управляющих символов. Источники:
`demo-middle`, `demo-bottom`, `demo-modal`. `company` является honeypot и должен
быть пустым. Допустимый JSON-запрос максимум **8192 байта**, включая chunked body.
Origin проверяется по списку, CORS не разрешён. HTTPS обязателен, кроме localhost.

Успех **только после положительного SMTP-ответа** для фиксированного получателя:

```json
{ "ok": true, "status": "sent", "requestId": "..." }
```

Это означает принятие почтовым сервером, а не гарантию попадания во входящие:
последующие bounce/спам-фильтры проверяются у почтового провайдера.
При replay подтверждённой заявки возвращается тот же статус без нового письма.

Ошибки: JSON `{ "ok": false, "code": "...", "requestId": "..." }`.
400: JSON/Idempotency-Key, 403: origin, 413: размер, 415: Content-Type,
422: поля/согласие/антиспам, 429: rate limit (`Retry-After`),
409: `in_progress`/`idempotency_conflict`, 503: SMTP/занятость/недоступность.
На nginx размер может отклоняться собственным 413; фронт корректно обработает
и такой ответ без ложного сообщения об успехе.

Фронт сохраняет поля и согласие при ошибке, блокирует повторное нажатие во время
запроса и повторяет неизменённую заявку с тем же Idempotency-Key. После успеха
кнопка блокируется до изменения данных. Таймаут браузера 35 секунд не означает,
что SMTP не принял письмо: повтор с тем же ключом безопасно проверяет состояние.

## Повторы, антиспам и хранение

- SQLite сохраняет ключи, HMAC отпечатки содержимого/IP и статусы. Сырые имена,
  контакты, тексты заявок и пароли в БД/логах не сохраняются. Письмо хранится уже
  у почтового провайдера в соответствии с утверждённой политикой.
- Idempotency-Key успешной заявки действует 24 часа; одинаковые имя/контакт
  из разных форм/с разными ключами подавляются 10 минут. Повтор после известного
  отказа SMTP разрешён с тем же ключом. Рейт-лимиты сохраняются при перезапуске.
- Если связь оборвалась во время DATA и результат SMTP неизвестен, статус
  `delivery_unknown` блокирует автоматическую повторную отправку на 7 дней.
  При перезапуске незавершённые `sending` также становятся `unknown`. Пользователю
  предлагается уточнить получение по контактам. Оператор сверяет очередь/логи
  провайдера и почту перед ручными действиями; не сбрасывать статус вслепую.
  SMTP не обеспечивает строгую exactly-once доставку.
- **Один процесс, одна инстанция.** Не включать PM2 cluster, несколько контейнеров
  или rolling overlap с одной SQLite: старт помечает незавершённые отправки
  предыдущего процесса как неопределённые. Остановить старый процесс перед новым.
- Хранить `/var/lib/sep-erp` на постоянном диске; не удалять SQLite/WAL при
  обновлении кода. Резервировать средствами SQLite или при остановленном сервисе,
  с правами `600`/каталогом `700`. Не менять HMAC-секрет при обычном деплое:
  ротация сбрасывает узнавание старых ключей/IP и требует согласованной процедуры.
- Логи содержат только событие, случайный requestId и безопасный код ошибки.
  Ответы не содержат SMTP-ошибки/секреты. Не добавлять логирование тела на nginx/APM.
- Honeypot, тайминг, origin, лимиты и дедупликация не заменяют CAPTCHA/WAF при
  целевой атаке: origin/тайминг бот может подделать. При необходимости подключить
  дополнительную защиту на reverse proxy, сохранив контракт API.

## Приёмка

1. `/healthz` и `/readyz` возвращают 200 локально.
2. Каждая из трёх форм: заполнить тестовые имя/контакт, отметить согласие;
   получить success и подтвердить письмо на `info@pksep.ru`. Для трёх разных
   писем менять тестовое имя, иначе корректно сработает дедупликация.
3. Проверить телефон и email; Reply-To только для email. Envelope и получатель
   всегда фиксированы.
4. Без согласия, с невалидным контактом или honeypot письма не отправляются.
5. Двойное нажатие/повтор запроса не создаёт дублей. Перезагрузка backend
   не теряет журнал. При недоступном SMTP нет success, поля сохранены и
   доступна повторная попытка; неопределённый DATA не отправляется повторно.
6. Проверить размер, 429, серверные права и отсутствие приватных файлов в HTTP.
7. Утвердить юридические документы: в лендинге пока черновики с предупреждением.

Исходный фронт изменяется в проекте SEP, затем `npm run build:erp` и
`npm run check:erp`. В репозиторий sites копируются готовая `ERP/`, backend и
эта инструкция. Пароли, БД, `node_modules/` и рабочие ENV не публикуются.
