# Отправка заявок SEP:Chat

Реализована по схеме СЭП ERP: все три формы обращаются к `POST /api/chat/leads`,
сервер отправляет письмо через Majordomo с обязательной авторизацией и TLS.
Отправитель и получатель жёстко фиксированы: `info@pksep.ru`; имя «SEP:Chat»,
тема «Заявка на демонстрацию SEP:Chat». Email посетителя используется только
как Reply-To. IMAP не требуется.

Адрес лендинга: **https://pksep.ru/chat/**. В ENV используется origin
`ALLOWED_ORIGINS=https://pksep.ru` (без `/chat/`). Формы отправляют запросы на
**https://pksep.ru/api/chat/leads**, не на `/chat/api/chat/leads`.

**Код и локальные тесты не означают запуск на production.** Нужны серверные ENV,
процесс Node.js и reverse proxy. Реальное поступление письма в ящик проверяется
после выкладки отдельно. До подключения API интерфейс честно показывает ошибку.

## Установка DevOps

1. Разместить содержимое `chat/` по адресу `https://pksep.ru/chat/`, сохраняя
   относительные пути CSS/JS/изображений. `backend/`, `deploy/`, ENV, SQLite и
   зависимости должны находиться вне document root. Не публиковать тестовые
   `logo-compare.html` и `mobile-preview.html`.
2. Требуется Node.js **24.13+**, npm, Linux/systemd и исходящий TCP 465.
   Разместить `backend/chat/` в `/opt/sep-chat/backend/chat` (без локальных
   `node_modules` и данных), затем:

   ```sh
   cd /opt/sep-chat/backend/chat
   npm ci --omit=dev --ignore-scripts
   npm test
   ```

   Тесты API используют локальный SMTP, не реальный ящик.
3. Создать системного пользователя `sep-chat`. Дать только чтение кода и
   зависимостей. Скопировать `.env.example` в `/etc/sep-chat/mail.env`,
   права `600`, владелец `root` (systemd читает ENV до смены пользователя).
   Не использовать старый `deploy/chat/.env`: в нём нет полного нового контракта.
4. На сервере заполнить `SMTP_PASSWORD` и отдельный случайный `LEADS_HMAC_SECRET`
   длиной минимум 32 символа (`openssl rand -hex 32`). Не присылать секреты в чат,
   не сохранять в Git/логах/аргументах команд. Оставить
   `ALLOWED_ORIGINS=https://pksep.ru`: это origin сайта, без пути `/chat/`
   и завершающего `/`.
5. Проверить `command -v node` и `node --version`; исправить путь `/usr/bin/node`
   в `sep-chat.service`, если требуется. Установить unit в
   `/etc/systemd/system/sep-chat.service`:

   ```sh
   sudo systemctl daemon-reload
   sudo systemctl enable --now sep-chat
   sudo systemctl status sep-chat
   curl --fail http://127.0.0.1:3002/healthz
   curl --fail http://127.0.0.1:3002/readyz
   ```

   `healthz` проверяет процесс, `readyz` подключение/авторизацию SMTP с кешем
   30 секунд, но не доставку во входящие. Не публиковать эти маршруты.
6. Добавить `nginx.conf.example` в действующий HTTPS server block `pksep.ru`
   на уровне server, не внутрь `location /chat/`. Не
   заменять весь конфиг и не менять `/api/leads` и порт 3001 ERP. Правила запрета
   `/backend/` и `/deploy/` не дублировать, если уже есть. Выполнить `nginx -t`,
   затем reload. Порт 3002 доступен только на `127.0.0.1`, не открывать наружу.
   Nginx должен перезаписывать X-Real-IP, а не доверять клиентскому заголовку.
7. Отправить согласованные тестовые заявки из всех трёх форм и вручную
   подтвердить их получение на `info@pksep.ru`, включая папку спама. Для трёх
   отдельных писем менять тестовое имя, иначе сработает защита от дублей.
   Проверить SPF/DKIM/DMARC и утверждённые юридические документы.

## ENV

Полный шаблон: [.env.example](.env.example). Основные параметры:

- `HOST=127.0.0.1`, `PORT=3002`, `TRUST_PROXY=true` только за закрытым nginx.
- `ALLOWED_ORIGINS`: точные HTTPS origin, HTTP допускается только для localhost.
- `SMTP_HOST=smtp.majordomo.ru`, `SMTP_PORT=465`, `SMTP_SECURE=true`: TLS сразу,
  проверка сертификата включена. Для 587 `false` включает обязательный STARTTLS.
- `SMTP_USER=info@pksep.ru`, `SMTP_PASSWORD`: обязательная авторизация.
- `MAIL_FROM`, `MAIL_TO`: только `info@pksep.ru`, иные значения отклоняются.
- `LEADS_HMAC_SECRET`: постоянный секрет минимум 32 символа, отдельный от ERP.
- `LEADS_DB_PATH=/var/lib/sep-chat/leads.sqlite`: постоянное хранилище вне сайта.
- `LEADS_RATE_LIMIT=5`: попыток с IP за 10 минут, включая невалидные запросы.
- `LEADS_GLOBAL_RATE_LIMIT=100`: общий лимит за 10 минут.
- `LEADS_MIN_FORM_MS=2000`, `LEADS_MAX_CONCURRENT=3`.

Логические значения строго `true`/`false`. Прежние `SMTP_AUTH`/`MAIL_FROM_NAME`
не нужны: авторизация обязательна, имя отправителя фиксировано в коде.
Без пароля/секрета сервис не запускается. Не отключать проверку TLS.

## Контракт и поведение

`POST /api/chat/leads`, `Content-Type: application/json`, разрешённый Origin,
`Idempotency-Key: <UUID v4>` и JSON:

```json
{"name":"Тест","contact":"visitor@example.com","consent":true,"source":"demo-middle","company":"","elapsedMs":4000}
```

Имя 1..100 символов, контакт до 150: email или телефон 10..15 цифр, без
управляющих символов; согласие строго `true`. Источники `demo-middle`,
`demo-bottom`, `demo-modal`. `company` скрытая антиспам-ловушка, должна быть
пустой. JSON до 8192 байт, возраст формы от 2000 мс. CORS не разрешён.

Только принятие фиксированного получателя SMTP даёт
`{"ok":true,"status":"sent","requestId":"..."}`. Это не гарантия попадания
во входящие: дальнейшие bounce/спам проверяются у провайдера.
Ошибки возвращают `ok:false`, безопасный `code` и `requestId`; коды HTTP
400/403/413/415/422/429/409/503. Сырые ошибки SMTP и данные заявок не выдаются.

Фронт сохраняет данные при ошибке, блокирует повторное нажатие во время отправки,
сохраняет ключ для неизменённой повторной попытки. После успеха кнопка отключена
до изменения данных. Закрытие/открытие модалки не сбрасывает активную заявку.
Таймаут браузера 35 секунд не означает, что письмо не принято; повтор с тем же
ключом проверяет состояние без слепой повторной отправки.

## Хранение и эксплуатация

- SQLite хранит только keyed HMAC отпечатки и статусы, не сырые имена/контакты.
  Логи: событие, случайный requestId и код ошибки. Не включать SMTP debug или
  запись тела запроса в nginx/APM. Само письмо хранится у почтового провайдера.
- Ключ успешной заявки действует 24 часа; одинаковые имя/контакт из разных
  форм подавляются 10 минут. Отказ до SMTP acceptance допускает повтор.
- При неопределённом результате DATA повторы блокируются на 7 дней
  (`delivery_unknown`). Незавершённые отправки после рестарта тоже неопределённы.
  Оператор сначала проверяет почту/очередь провайдера, не сбрасывает статус вслепую.
  SMTP не гарантирует строго однократную доставку.
- **Один процесс / одна инстанция**, не PM2 cluster и не rolling overlap с общей
  SQLite. Останавливать старый процесс до запуска нового.
- Сохранять `/var/lib/sep-chat` при обновлении, каталог `700`, БД `600`.
  Резервировать средствами SQLite или при остановке сервиса. Не удалять WAL
  и не менять HMAC-секрет при обычном деплое: это сбрасывает защиту от повторов.
- Origin/honeypot/тайминг/лимиты не заменяют CAPTCHA или WAF при целевой атаке.

## Локальная проверка

См. [инструкцию лендинга](../../chat/README.md). `npm test` проверяет API,
SQLite, антиспам, рестарты и SMTP-протокол на тестовом сервере. Для браузерных
проверок установить dev-зависимости (`npm ci --ignore-scripts`) и Chrome,
выполнить `npm run test:browser`. Проверяются все формы на 1440/390 px,
ошибки, согласие, повторы, закрытие модалки во время отправки. Реальных писем
автотесты не отправляют. Node 24 может предупреждать об experimental SQLite API.
